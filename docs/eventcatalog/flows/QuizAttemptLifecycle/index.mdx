## Overview

This is the hosted design from `docs/ORCHESTRATION.md`: **one shared main app** (a Go monolith split by domain)
and **one throwaway sandbox VM per active quiz attempt**, with at most one active VM per user.

<NodeGraph />

## Reading the graph

1. **Start.** The attempt is saved, and the sandbox domain claims a warm VM through the Fly Machines API (or creates one).
2. **Setup.** The agent runs each task's `setup.sh` against the kind cluster in that VM.
3. **Work.** The browser's terminal websocket goes to the main app, which proxies it over Fly's private network to the
   agent's shell. The VM is never public.
4. **Grade.** Check or Submit runs `check.sh` through the agent, and the `PASS/FAIL <pts>` lines become the stored score.
5. **End.** On submit, deadline or idle timeout the VM is marked expired, and the reaper destroys it.

The terminal path in detail, as it works locally today, is documented on [Web Terminal](/docs/services/WebTerminal/0.0.1)
and [cka-sim Server](/docs/services/CkaSimServer/0.0.1).
